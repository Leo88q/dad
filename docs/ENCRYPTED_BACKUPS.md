# Шифрованные резервные копии и контроль их состояния

Реализовано и проверено на временной БД в Node. Docker/Compose и внешний сервер в этой среде не запускались. Подготовленная конфигурация не означает, что копии уже создаются у оператора.

## Что делает цикл

1. Получает согласованный SQLite online snapshot, включая зафиксированный WAL, не останавливая приложение.
2. Проверяет integrity_check, foreign_key_check и обязательные таблицы.
3. Потоково шифрует AES-256-GCM со случайным 96-битным nonce и аутентифицированной версией формата. Ключ — случайные 256 бит, не пароль.
4. Публикует архив без перезаписи существующего файла. Права 0600; временные каталоги закрытые.
5. Расшифровывает архив во временную копию, повторно проверяет SQLite и сравнивает SHA-256 с исходным снимком.
6. Только после успеха удаляет лишние старые архивы своего формата. Новый архив не удаляется при откате часов. Посторонние файлы не ротируются.

Контрольная сумма в статусе помогает при передаче; защита от подмены обеспечивается тегом GCM, а не открытой суммой. Статус не заменяет самостоятельную проверку архива после внешнего копирования.

Одновременные циклы в одном каталоге блокируются каталогом `.backup-cycle.lock`. После SIGKILL/аварии блокировка может остаться: это безопасный отказ, который нужно заметить по неуспешному healthcheck. Удалять её разрешено **только после подтверждения отсутствия работающего backup-worker/ручного цикла**. При обычном завершении она снимается автоматически. Оставшийся временный plaintext после аварии не считается архивом: в Compose он находится в tmpfs контейнера; в прямом Node нужно контролировать закрытый временный каталог и очистку после аварий. Plaintext существует во время проверки — это не end-to-end шифрование работающей БД.

## Ключ

Создать на сервере в закрытом каталоге (команда не выводит ключ и отказывается перезаписывать файл):

```sh
mkdir -p /srv/ryadom/secrets
chmod 700 /srv/ryadom/secrets
node scripts/backup-key.js /srv/ryadom/secrets/backup-key
```

Для Compose файл должен быть доступен UID 1000 контейнера, например через `chown 1000:1000` на обычном rootful Docker. Права самого файла — 0600 или 0400. При rootless/user namespace настройте реальное соответствие UID; не открывайте чтение всем ради обхода ошибки. `.env` содержит **путь**, не ключ. В Git/чат/логи ключ не передавать.

Хранить независимую защищённую офлайн-копию ключа отдельно от архивов. Потеря всех экземпляров ключа делает архивы невосстановимыми. Компрометация ключа требует нового ключа и отдельного каталога новых архивов. Старые ключи нужны до окончания срока хранения старых архивов; не заменяйте единственный файл без сохранения старого ключа. Единого key-management сервиса в приложении нет.

## Автоматический запуск

`compose.yaml` включает `backup-worker` без tools-профиля. После подготовки ключа:

```sh
# В приватном .env задать абсолютный BACKUP_KEY_HOST_FILE
# и все обязательные production-настройки приложения.
docker compose config --quiet
docker compose up -d --build
# Проверить не только app, но и здоровье backup-worker:
docker compose ps
docker compose exec backup-worker node scripts/backup-health.js
```

Worker читает основной том read-only, сохраняет архивы в отдельный том app-backups и не имеет сети. Первая копия создаётся сразу. По умолчанию интервал 21600 секунд (6 часов), сохраняются 56 копий: примерно 14 дней при непрерывной успешной работе. **Это предложенные параметры, не утверждённый срок хранения или гарантия RPO.** Требуется решение оператора. BACKUP_INTERVAL_SECONDS: 60..604800; BACKUP_KEEP: 1..3650. Неверные числа не принимаются. Ошибочный цикл повторяется не позже чем через 5 минут. SIGTERM прекращает ожидание; начавшийся цикл сначала заканчивается.

Прямой Node, если окружение уже задано:

```sh
BACKUP_KEY_FILE=/private/key BACKUP_DIR=/private/encrypted DATA_DIR=/srv/ryadom/data npm run backup:encrypted
# Постоянный сервис под systemd/process supervisor:
npm run backup:daemon
npm run backup:health
```

Healthcheck неуспешен при последней ошибке, отсутствующем архиве или возрасте успешной проверки больше интервала + 10 минут. Проверяет наличие файла, но не расшифровывает его заново на каждом запросе. **Docker unhealthy сам по себе не отправляет оповещение и не перезапускает живой worker.** Подключите внешний мониторинг статуса контейнера/кода выхода healthcheck, свободного места и факта внешней передачи.

## Внешняя копия — обязательная часть эксплуатации

Локальный Docker volume не защищает от потери сервера. Нужно отдельно настроить передачу **только `.sqlite.enc`** в независимое хранилище с ограниченными правами, своей ротацией и контролем успеха. Шифрованный worker намеренно изолирован от сети. Поставщик хранилища, доступы и фактическая передача здесь не настроены. Не передавайте ключ вместе с архивом. Не включайте незашифрованные `/tmp` или старые ручные `.sqlite` в общий upload.

## Расшифровка и восстановление

В закрытом рабочем каталоге с достаточным свободным местом:

```sh
BACKUP_KEY_FILE=/offline/backup-key node scripts/decrypt-backup.js /secure/ryadom-TIMESTAMP-ID.sqlite.enc /private/snapshot.sqlite
DATA_DIR=/srv/ryadom/restored node scripts/restore.js /private/snapshot.sqlite --confirm-stopped
```

Выходной файл и `.sha256` не перезаписываются. Неверный ключ, изменённый заголовок/шифротекст или обрезанный файл дают ошибку без публикации plaintext.

**Никогда не запускайте приложение прямо на расшифрованном snapshot:** в нём сохранены старые доступы. Только `restore.js` отзывает их до публикации в новом пустом DATA_DIR и включает обязательную блокировку проверки. Далее выполнить весь [RECOVERY.md](RECOVERY.md): сверить удаления после даты архива, проверить содержимое, явно выпустить восстановление и дождаться защитного окна. Удалить временные plaintext и `.sha256` после завершения по принятой политике; обычное удаление файла не гарантирует стирание с физического носителя.

## Регулярная аварийная репетиция

На отдельном закрытом стенде взять архив **из внешнего хранилища**, расшифровать, запустить hardening restore, подтвердить блокировку старых доступов и провести проверку новых MAX-входов после review/release. Записать дату архива, длительность восстановления, потерянный интервал данных и исполнителя, без пользовательского содержимого в отчёте. Онлайн round-trip каждого архива не заменяет эту репетицию.

## Автоматические проверки

Тесты: WAL snapshot, приватные права, отсутствие открытой SQLite в архивном каталоге, неверный ключ, подмена, обрезание, запрет перезаписи, ротация только после успеха, блокировка конкурирующих циклов, CLI/статус/устаревание, немедленный первый цикл и SIGTERM, расшифровка → hardened restore с обязательным review lock и отзывом старых доступов.

В CI добавлена сборка образа, отказ запуска production без конфигурации и smoke контейнера с шифрованной копией. Успех этого CI в GitHub пока отдельно не подтверждён; реальный Compose/TLS/MAX остаются отдельной приёмкой.
