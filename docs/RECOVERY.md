# Восстановление после сбоя без возврата старых доступов

Режим восстановления теперь **закрыт по умолчанию**. Это реализованный механизм и локально проверенный runbook; производственные копии, внеплощадочное хранение и дежурства здесь не развёрнуты.

## Что делает restore

1. Требует `--confirm-stopped`, проверяет SHA-256 архива и отказывается перезаписывать sqlite/WAL/SHM/journal существующей базы.
2. Копирует архив в случайный приватный временный файл в целевом каталоге. Проверяет хеш скопированных байтов, целостность и таблицы. Исходный архив не меняется.
3. В транзакции удаляет все access_sessions, device_codes и max_launches, заменяет legacy-ключи неизвестными случайными хешами, сбрасывает recovery-коды и перевыпускает приглашения всех пар.
4. Сохраняет содержимое занятий/договорённостей/избранного и привязки MAX, но устанавливает обязательный **review lock**. Запуск сервера сам этот замок не снимает.
5. Проверяет целостность и foreign_key_check, закрывает SQLite и публикует готовый файл атомарной эксклюзивной hard link в том же каталоге. Если публикация не поддерживается файловой системой, операция завершается ошибкой, не используется опасный fallback с перезаписью.

В stdout возвращаются sourceSha256 и SHA-256 изменённого восстановленного файла. Они различаются: восстановление намеренно меняет доступы. Это не новый архив с прежней контрольной суммой. Диагностика не содержит выданных ключей/кодов.

## Порядок действий оператора

1. Объявить обслуживание, остановить приложение. Не восстанавливать поверх работающего app-data.
2. Выбрать **пустой** постоянный каталог/том; защитить архив и каталог правами доступа.
3. Восстановить:

```sh
DATA_DIR=/srv/ryadom/data-restored npm run restore -- /secure-backups/ИМЯ.sqlite --confirm-stopped
```

4. **До открытия доступа сверить удаления и обращения пользователей после даты архива.** Архив может содержать удалённые впоследствии данные, старый состав пары/привязки. Автоматической сверки с внешним журналом нет. Удалить/скорректировать такие данные по утверждённой процедуре оператора. Подтверждение флагом не выполняет эту работу за человека. Не подтверждайте проверку, если не можете установить корректное состояние.
5. Проверить восстановленные данные в изолированной среде. Можно запустить сервер: `/healthz` остаётся 200 при доступной БД, `/readyz` возвращает 503, все API кроме публичной конфигурации возвращают 503. Пользователь видит экран временной недоступности. Токены, recovery и приглашения ещё до этого уже аннулированы.
6. После завершения проверки снова остановить приложение и явно выпустить восстановление:

```sh
DATA_DIR=/srv/ryadom/data-restored npm run release-restore -- --confirm-stopped --confirm-reviewed
```

7. Команда сообщает `opensAt`. Запустить приложение с **полным production-окружением** и DATA_DIR нового каталога. Не подменяйте production-параметры примером разработки. Пример при настройках в защищённом .env:

```sh
node --env-file=.env scripts/preflight.js
# DATA_DIR в .env должен указывать на выбранный восстановленный каталог.
node --env-file=.env server.js
```

До opensAt readiness/API всё ещё 503. После opensAt проверяются `/readyz`, свежий вход MAX, пара, договорённости, избранное, реальные копии и оповещения. Docker healthcheck также должен дождаться готовности; в Compose прокси зависит от healthy app. Docker-процесс этой сессией не проверялся.

**Оба флага — утверждения оператора, не обнаружение работающего процесса и не юридическая проверка.** Нет команды отменить сброс старых доступов и нет режима `--preserve-credentials`.

## Поведение MAX и пользователей

- Release устанавливает минимальный auth_date позже текущего времени на полную минуту (61 секунда с округлением), чтобы исключить также старые подписанные запуски с допустимым опережением часов до 60 секунд. До этой даты сервис остаётся закрытым.
- После opensAt пользователь закрывает и заново открывает Mini App. Старый initData отвергается даже с правильной HMAC-подписью. Сохранённый отозванный bearer не выдаёт доступ; свежая MAX-идентичность создаёт новую сессию того же проверенного профиля.
- Сброс ключей не удаляет сеансы самого мессенджера. Если аккаунт MAX скомпрометирован, нужно защитить его средствами MAX.
- Старые коды восстановления/подключения и ссылки приглашений **не работают**. Новый код восстановления можно получить в настройках после свежего входа MAX; новые приглашения — в «Наша пара».
- Браузерный профиль **без привязки MAX** после такого сброса нельзя открыть старым кодом. Автоматического восстановления личности по имени или доступа родственника нет. До выпуска оператор должен решить такие случаи по проверяемой процедуре; не раздавать доступ по одному совпадению имени. Основной production-канал продукта — MAX.
- Изменения и прогресс после даты выбранной копии могут быть утрачены. Сброс доступов не восстанавливает эти данные.

## Что остаётся обязательным

- Защищённые внешние копии и подтверждённые сроки хранения, мониторинг возраста/ошибок копий, периодические реальные пробы восстановления.
- Процесс/внешний журнал сверки удалений и изменений после даты архива. Review lock лишь не позволяет открыть архив по ошибке — он не выполняет автоматическое удаление этих данных.
- Проверка времени сервера, фактических RPO/RTO, сетевого доступа и настоящих клиентов MAX.
- Контрольная сумма выявляет повреждение/изменение, **не доказывает аутентичность** архива. Доступ к архиву и его checksum должен быть защищён.

## Автоматические проверки

`test/recovery.test.js`: сброс всех старых возможностей доступа, сохранение данных, транзакционный откат при ошибке, review lock, ожидание до opensAt и запрет повторного release. Полный HTTP-сценарий: работающий сервер → online backup → отзыв ключа → остановка → restore в новый каталог → 503 → отказ выпуска без подтверждения → release → 503 до opensAt → запрет старых токенов/кодов/приглашения/initData → новый подписанный MAX-вход в сохранённый профиль с избранным.

В тесте ожидание часов моделируется изменением **только тестовой базы**; в production обхода cooldown нет. Настоящие токены MAX и производственные данные не используются.
