# Постоянные ограничения запросов

## Реализация

Вместо трёх Map в памяти сервер использует `DATA_DIR/security.sqlite` (SQLite WAL, приватные права 0600). Счётчики и случайный серверный HMAC-ключ переживают обычный рестарт. `BEGIN IMMEDIATE` делает проверку и увеличение атомарными для процессов, обращающихся к одному файлу на локальном диске. Изменение счётчика подтверждается до обработки запроса.

Это **не распределённая система для нескольких серверов** и не основание запускать весь продукт в нескольких экземплярах: другие части приложения сохраняют ограничения однопроцессной архитектуры. SQLite нельзя размещать на произвольном сетевом/NFS-диске. При горизонтальном масштабировании потребуется общий limiter и отдельная архитектурная проверка.

## Политики

- Все `/api`: 180 запросов за окно 60 секунд на сетевой источник.
- `/api/recover`: дополнительно 5 попыток за 15 минут.
- `/api/connect-device`: дополнительно 10 попыток за 15 минут.

Считаются все попытки, не только неудачные; специальные лимиты независимы друг от друга, общий применяется к ним тоже. Окно начинается с первого запроса; это фиксированное окно, не sliding window. На границе возможен более плотный поток — это известное свойство, не защита от всех видов атак.

Превышение — HTTP 429 с `Retry-After` (целые секунды до конца окна, минимум 1). Неисправность/блокировка хранилища — HTTP 503 с `Retry-After: 60`, а не пропуск защиты. SQLite ждёт занятую запись до 5 секунд. Объём ограничен 50 000 одновременно хранимых ключей: при заполнении неизвестный ключ получает 503, действующие ограничения не вытесняются. Истёкшие записи очищаются при последующих обращениях, не чаще минуты. При отсутствии трафика отдельного фонового удаления нет; сроки фактического хранения и поведение файлов WAL нужно учитывать в политике оператора. SQL DELETE не гарантирует физического стирания носителя.

## Псевдонимизация сети

Исходные IP, имена, ответы, токены и коды в таблицу лимитов не записываются. Ключ счётчика — HMAC-SHA256 от области действия и нормализованного сетевого источника с отдельным случайным секретом.

IPv4 и его IPv4-mapped IPv6 представления используют одну квоту. IPv6 объединяется по /64, чтобы смена младшей части адреса не обнуляла ограничение. Это может объединять нескольких людей. HMAC-секрет хранится в той же закрытой служебной БД: это псевдонимизация, **не анонимизация** от оператора/того, кто получил файл вместе с ключом. Счётчики не связаны с профилями и не используются как аналитика.

Общий NAT и IPv6 /64 делят квоты. Перед подключением большого учреждения/сети требуется измерить реальный поток и проверить политику; лимит нельзя считать рассчитанной ёмкостью промышленного сервиса.

## Reverse proxy

По умолчанию Express не доверяет X-Forwarded-For. В Compose Express доверяет только backend 172.29.0.0/24; Nginx доверяет front 172.28.0.0/24 от Caddy. Прямые порты приложения и edge наружу не опубликованы. Перед постоянными лимитами действует [L7 edge](DDOS.md). При другом размещении TRUST_PROXY должен соответствовать конкретным доверенным прокси/IP/CIDR. Не выставляйте доверие всем адресам и не открывайте обход прокси: иначе клиент сможет менять источник и обходить ограничения. Подмена X-Forwarded-For без доверенного прокси проверяется HTTP-тестом.

Ограничители стоят после парсера JSON и не ограничивают статические файлы/сетевые соединения. Они не заменяют защиту на reverse proxy, инфраструктурный WAF/DDoS, ограничение размера/времени соединения и независимый аудит.

## Эксплуатация и восстановление

- Не удаляйте security.sqlite при обычном обновлении: это обнулит лимиты. Служебный файл живёт на том же постоянном томе, что данные.
- `/readyz` дополнительно проверяет доступность чтения служебной БД. Это не пробная запись и не полноценная проверка свободного места/диска.
- Не выставляйте служебную БД через static/web и не добавляйте в пользовательский экспорт.
- Штатный зашифрованный backup содержит основную БД приложения, **не security.sqlite**. После восстановления в совершенно новый DATA_DIR создаются новые сетевые счётчики. Обязательная блокировка восстановления основного продукта остаётся в силе. При переносе старого служебного файла необходим согласованный SQLite backup, нельзя копировать живой файл без WAL.
- Учитывайте обработку сетевых псевдонимов до входа в документах оператора. Для production перед развёртыванием обновите опубликованную политику и DATA_POLICY_VERSION по утверждённому решению. Приложение не оформляет правовое основание автоматически.
- Версии ознакомления разработки обновлены: web `pilot-data-v3-security`, MAX `pilot-data-max-v2-security`. Старые записи не подменяются; требуется новое подтверждение через существующий механизм.

## Проверки

Шесть новых тестов: нормализация IPv4/IPv6, сохранение после открытия файла заново и точная граница окна, разные области/источники, предел вместимости и очистка, два реальных процесса на одной квоте, HTTP-рестарт и недоверенный X-Forwarded-For, HTTP 503 при занятой записи и восстановление после снятия блокировки. E2E получают отдельный каталог тестовых данных на каждый прогон: защита не отключается ради повторяемости тестов.
