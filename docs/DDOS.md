# Защита от HTTP-перегрузки и границы DDoS-защиты

## Реализованный слой

```
Интернет → Caddy (TLS, 80/443) → Nginx edge (8080, не опубликован) → Node (3000, не опубликован)
```

В Compose Caddy и edge находятся в `front` (172.28.0.0/24), edge и приложение — в отдельной `backend` (172.29.0.0/24, internal). Caddy не имеет прямого сетевого подключения к приложению. Nginx работает UID 101 без capabilities, с read-only root, tmpfs для временных файлов, лимитами RAM 256 MiB, CPU 1, PID 128 и файловых дескрипторов. Это ограничения ресурсов контейнера, не обещание ёмкости сервера.

Входные правила работают **до Express и SQLite**. Постоянные счётчики приложения остаются вторым слоем. Предпросмотр с прямым `npm start` не проходит через этот edge: включение предусмотрено в серверном Compose, а не в публичном preview Arena.

## Политики по умолчанию

| Защита | Настройка |
|---|---|
| Все запросы от одного IP | 30/с, burst 60 |
| Все запросы суммарно | 200/с, burst 100 |
| API от одного IP | 5/с, burst 20 |
| API суммарно, включая разные источники | 40/с, burst 40 |
| MAX-вход, восстановление, подключение устройства | общая зона 30/мин на IP, burst 10, дополнительно к API |
| Одновременно обрабатываемые запросы от одного IP | 20 |
| Одновременно обрабатываемые запросы суммарно | 1024 |
| Тело запроса | не более 32 KiB, буферизация до передачи Node |
| Чтение заголовков | 5 секунд |
| Ожидание очередной части тела | 10 секунд |
| Keep-alive Nginx | 15 секунд, до 100 запросов на соединение |
| Соединение с Node / чтение ответа | 3 / 20 секунд |

Nginx использует leaky-bucket с burst и `nodelay`: это **не** число запросов в фиксированную минуту. Первый всплеск допускается в пределах burst, лишние отклоняются сразу. Политики shared-memory общие для двух worker-процессов Nginx, но сбрасываются после полного перезапуска контейнера. Постоянные квоты Node сохраняются. Персональные IP-квоты edge не объединяют IPv6 /64; суммарная квота защищает также от смены множества адресов, а Node дополнительно группирует IPv6 /64.

В location с собственными limit_req родительские правила не наследуются: поэтому общие зоны явно включены во все защищённые locations через include-файлы. Префиксные locations входа включают вариант с завершающим `/`; маршруты Node регистрозависимы, чтобы альтернативный регистр не запускал обработчик вне соответствующей политики edge.

Превышение частоты возвращает JSON 429, Retry-After: 2 и X-Ryadom-Protection: edge-rate. Превышение одновременных запросов — JSON 503, Retry-After: 5, edge-capacity. Большое тело — JSON 413, edge-body. Ответы Node не перехватываются: его собственные 429 и точный Retry-After до конца окна сохраняются. Значения Retry-After edge — консервативная рекомендация, а не резервирование следующего запроса.

Caddy дополнительно ограничивает размер заголовков 16 KiB, время чтения заголовков/тела, записи ответа и idle. Таймаут тела Nginx — между операциями чтения, не абсолютный дедлайн всей загрузки; нельзя считать его полным решением для всех медленных атак. Незавершённые заголовки проверены отдельным TCP-тестом. Часть idle/неполных соединений ещё не входит в limit_conn; их ограничивают таймауты и общий бюджет worker_connections, а внешний TLS-прокси также должен защищаться на уровне инфраструктуры.

## Доверие к IP и обход фильтра

В текущей схеме Caddy принимает прямой публичный трафик и **перезаписывает X-Forwarded-For реальным адресом своего соединения**. Nginx доверяет этому заголовку только от сети front; в приложение передаёт один проверенный адрес, не входящую цепочку. Express доверяет только backend.

Нельзя публиковать 8080/3000, добавлять app в front, включать доверие всем прокси или открывать origin в обход внешнего фильтра. При смене подсетей одновременно обновить Compose, set_real_ip_from и TRUST_PROXY. Loopback-доверие в интеграционных тестах — тестовая подстановка, не production-конфигурация.

За NAT квота общая. Эти значения — консервативная исходная конфигурация, не измеренный максимум и не универсальная политика для учреждений/корпоративных сетей. Перед массовым запуском измерить реальный трафик, ложные отказы и задержки, затем менять `deploy/nginx/*.conf` с повторным прогоном тестов. Под нагрузкой global quota может отказать и добросовестным пользователям: без внешней классификации нельзя отличить всех атакующих.

## Логи и наблюдение

Nginx access-log содержит время, HTTP-статус, длительность и результат квоты. В формат не включены IP, URI/query, Authorization, initData, приглашения и User-Agent. Штатные сообщения limit_req не дублируются с IP в error-log (уровень crit). Логи контейнеров ограничены по размеру. Это правило для edge, не утверждение о политике всех внешних провайдеров и остальных компонентов.

Настроить внешние оповещения по росту 429/503, отказам upstream, CPU/RAM/перезапускам edge и доступности публичного `/readyz`. `/edge-health` проверяет только сам edge, не приложение. Docker healthcheck не отправляет уведомлений сам. Ошибки origin/сети необходимо отслеживать также вне сервера. Реальная маршрутизация уведомлений здесь не подключена.

## Что нужно для объёмного DDoS

**Реализовано смягчение HTTP-перегрузки (L7), не полная защита от любого DDoS.** Локальный Nginx не спасает, если атака насыщает канал, таблицу соединений ядра, TLS-прокси или инфраструктуру хостера. SYN/UDP/TLS-flood на уровне провайдера этим кодом не остановлены.

Для публичного запуска:

1. Подключить у хостера/фильтрующего провайдера L3/L4-защиту и при необходимости внешний L7/WAF, включая IPv6, а не только IPv4.
2. Если используется CDN/внешний прокси — закрыть origin от прямого доступа, разрешить 80/443 только его актуальным официальным CIDR и административный доступ только разрешённым адресам. Учитывать, что опубликованные Docker-порты могут обходить простые правила UFW: проверять фактическую цепочку Docker/DOCKER-USER/nftables у выбранного хостера.
3. Изменить текущую прямую схему Caddy: проверять заголовок реального клиента только от официальных доверенных сетей провайдера, передавать в Nginx **один подтверждённый client IP**, не произвольную цепочку. Текущий remote.host за CDN будет адресом CDN: без изменения все пользователи попадут в общую квоту. Не копировать список CIDR из случайного примера.
4. Проверить, что JavaScript/CAPTCHA challenge внешнего WAF не ломает MAX WebView и API-вход. Не отключать всю защиту API ради совместимости: выбрать поддерживаемые провайдером правила, проверить реальный MAX.
5. Согласовать контакты реагирования, допустимую деградацию, бюджет и действия при обходе фильтра.

Провайдер, домен, firewall и внешняя фильтрация в этой сессии **не настроены**. Подготовленный Compose сам их не включает.

## Включение и проверка

После настройки production `.env` и ключа backup:

```sh
docker compose config --quiet
docker compose up -d --build
docker compose exec edge nginx -t
docker compose ps
# Проверить публичный /readyz, реальные MAX-вход/приглашение и 2 устройства.
```

Проверять атаки только на собственном изолированном стенде, не на действующем пользовательском сервисе и не на чужих адресах. Локальная команда:

```sh
npm run test:edge
```

Первый запуск собирает тестовый Nginx 1.30.6 из закреплённого исходного архива GitHub с проверкой SHA-256; нужны POSIX shell, curl, tar, sha256sum, make и C-компилятор. Артефакты остаются только в игнорируемой `.cache`. Можно указать собственный NGINX_BIN. Production использует официальный контейнер, не этот тестовый бинарник.

Семь проверок с настоящим Nginx и локальным upstream: нормальная передача и доверие к IP, ранний 413, всплеск с поддельными заголовками, суммарный лимит разных источников, auth с trailing slash, конкурентные медленные ответы и незавершённые TCP-заголовки. Нагрузочные запросы направлены только на локальные временные порты. Это не тест насыщения канала и не результат аудита DDoS-провайдера.

CI дополнен этими тестами, проверкой read-only/non-root контейнера edge, связки с приложением и `caddy validate`. Docker здесь отсутствует: контейнерная часть/реальный TLS пока не подтверждены, несмотря на успешные локальные Nginx-тесты.
