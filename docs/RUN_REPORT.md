# Большой прогон и блок реализации

Дата: **4 ноября 2026 года**. Репозиторий: Рядом. Среда: Node.js 22.22.3, Linux, headless Chromium 143 из npm-пакета. Проверялась локальная версия, не промышленный сервер.

## Что реализовано в этом блоке

1. Библиотека увеличена с 6 до **14** занятий: 8 безопасность, 3 семейные истории, 3 освоение телефона.
2. Разделены окончания: семейный разговор без навязанной договорённости, обучающее занятие с добровольной памяткой или завершением без неё.
3. Включаемые пользователем предложения повторений на главной: 3, 10, 30 дней после очередного завершения. Нет внешних уведомлений и штрафов.
4. Техническая запись версии/даты согласия пилота и повторное ознакомление для существующих профилей без записи.
5. Выход отзывает ключ на сервере. Восстановление по сохранённому коду сохраняет данные.
6. Online backup SQLite/WAL, checksum, проверка целостности и безопасное восстановление в пустой каталог.
7. Подготовлены Docker/Compose/Caddy, healthcheck, завершение по сигналу, инструкция эксплуатации и протокол исследования с людьми.
8. Настроены реальные браузерные тесты и изолированный smoke-прогон нагрузки; CI расширен до полного прогона.
9. Дополнительно реализовано управление пятью независимыми устройствами профиля: одноразовый код подключения на 10 минут, список, переименование, индивидуальный/массовый отзыв, аварийный сброс всех устройств при восстановлении. Перенос старого ключа не позволяет заново войти после отзыва. Два устройства одного профиля не обходят независимое согласие близкого.
10. Версия технического согласия обновлена до pilot-data-v2-devices с явным описанием метаданных подключений; старая запись не подменяется новой автоматически.

11. После уточнения канала реализован MAX Mini App: Bridge, серверный HMAC initData/возраст/replay, явная привязка профиля и согласие pilot-data-max-v1, подписанные startapp-приглашения, native share/BackButton/SecureStorage, одноразовое HTTPS-скачивание. Реальные бот и клиенты MAX ещё не настроены/проверены; инструкция docs/MAX.md.

### Безопасное восстановление

Restore теперь работает с приватным временным файлом, проверяет хеш скопированных байтов, integrity/FK и аннулирует сессии/legacy-ключи/recovery/коды подключения/приглашения до атомарной эксклюзивной публикации. После запуска API закрыт review lock, readiness=503. Release только с подтверждениями остановки/сверки; затем защитное окно 61 секунда исключает прежние MAX-подписи. История/избранное/проверенные MAX-привязки сохраняются за закрытым доступом.

Добавлены 3 unit-теста (сброс/сохранность, review+время, rollback) и полный HTTP/CLI сценарий backup → отзыв ключа → restore → 503 → release → cooldown → отказ старых ключей/кодов/приглашений/initData → новый MAX-вход с сохранённым избранным. Прежний тест backup/restore также проходит. Автоматической сверки удалённых после даты копии данных нет: требуется подтверждённая работа оператора, см. RECOVERY.md. Это не проверка восстановления настоящей промышленной базы.

### Production-конфигурация и UI сервиса

Конфигурация production теперь проверяется до открытия БД: обязательны MAX_ONLY, секрет и username, постоянный абсолютный путь, HTTPS-origin, оператор, контакт поддержки, адреса документов и их версия. Preflight не печатает секрет и проверяет production независимо от NODE_ENV оболочки. В UI публичного режима показываются сведения оператора и ссылки, не пилотные заглушки. В тестовом окружении они не выдумываются.

Изменение DATA_POLICY_VERSION требует нового принятия: HTTP-тест настоящего production-сервера с фиктивным бот-токеном проверяет запись max-data-revision-1, перезапуск с revision-2, сохранность старой записи, запрос согласия и обновление только после подтверждения. Проверены публичная конфигурация без токена, HSTS, запрет обычной регистрации, readiness 200 и 503 при недоступном каталоге. Отдельно проверены невалидные настройки/ссылки, скрытие токена в CLI и UI реквизитов/ссылок. Всего добавлены 5 unit/API/CLI и 1 DOM-тест.

Docker healthcheck переключён на /readyz. Реальные Docker/TLS, операторские документы и настоящий MAX этим не проверены.

## Что нашёл первый браузерный прогон

- Часть второстепенного текста не проходила проверку контраста — цвета исправлены.
- Chromium сохранял файл с кириллическим именем как `download` — имена файлов изменены на стабильные ASCII, русское содержимое сохранено.
- Второй удалённый участник при уже данном первом ответе мог попадать сразу к вариантам, минуя историю — восстановление этапа исправлено, теперь он читает историю прежде своего ответа.

После исправлений весь прогон повторён успешно. Проверки не отключались для маскировки этих ошибок.

## Что этим прогоном не подтверждено

- Реальные телефоны, Safari/Firefox, встроенные браузеры MAX/Telegram, скринридеры.
- Понятность и полезность для людей 60+, отсутствие ощущения контроля.
- Экспертная точность контента и юридическая корректность документов.
- Работа Docker/Compose/Caddy и внешнего HTTPS: Docker в среде отсутствует.
- Рабочие расписания, шифрованные внешние копии, мониторинг, поддержка, откат производственной базы.
- Настоящее initData из клиента MAX, native Bridge/CDN/скачивание на Android/iOS/web, регистрация бота и публикация/модерация. Код MAX интеграции покрыт локальными тестами; Telegram не входит в целевой релиз.
- Успешный запуск настроенного workflow на GitHub.

## Промышленная эксплуатация: постоянные лимиты запросов

Три ограничителя Map заменены на отдельную `security.sqlite`: HMAC-псевдонимы сети, приватный файл, атомарная проверка/увеличение, сохранение при рестарте, ограничение вместимости и удаление истёкших записей при трафике. Retry-After есть у всех отказов по квоте; при недоступной записи — fail-closed 503. IPv4-mapped представления объединены, IPv6 группируется по /64. В пользовательском окне данных описана обработка; версии ознакомления разработки обновлены без подмены старых записей. Production требует утверждения документов и изменения DATA_POLICY_VERSION оператором.

Шесть новых тестов включают два отдельных процесса, реальный HTTP-рестарт, подменённые forwarding-заголовки без доверенного прокси, заполнение хранилища, точную границу окна и реальную блокировку SQLite с последующим восстановлением. E2E используют уникальные каталоги на прогон, не отключая постоянную защиту.

Последний полный `npm run test:all`: **69/69 Node, 28/28 Chromium E2E**, 120 запросов / 12 пар / 3 одновременно / 0 неуспешных пар. Локально 323 мс, p50 7 мс, p95 17 мс, максимум 55 мс. Не промышленный SLA и не предельная нагрузка. Архитектура остаётся односерверной, внешний аудит/WAF/DDoS и проверка MAX не заменены этим блоком.

## L7-защита от HTTP-перегрузки

Добавлен Nginx edge до Node: индивидуальные и суммарные leaky-bucket квоты, отдельная зона входа/восстановления/подключения, предел одновременно обрабатываемых запросов, тело 32 KiB, таймауты/буферизация, JSON 429/503/413 и Retry-After. Prefix locations покрывают trailing slash, Node переведён на регистрозависимые маршруты. Верхний регистр API проверен на 404. В Compose front/backend разделены, у edge/app нет публичных портов, edge работает non-root/read-only с ограничением ресурсов. Caddy перезаписывает X-Forwarded-For адресом прямого клиента, edge доверяет только front, Node — только backend.

Для реальной локальной проверки собран Nginx **1.30.6** из закреплённого исходного архива GitHub, SHA-256 проверяется bootstrap-скриптом. Семь интеграционных тестов: обычная передача и граница доверия IP, ранний 413 без запроса в upstream, per-source burst с поддельным XFF, aggregate burst разных источников, auth/trailing slash, одновременные медленные ответы и незавершённые TCP-заголовки с фактическим таймаутом. Тесты только на временных loopback-портах. Первый вариант теста concurrent burst конкурировал также с лимитом соединений: для независимой проверки частоты заменён на серии по 5 запросов, проверка соединений оставлена отдельной.

Последний полный `npm run test:all`: **69/69 Node, 28/28 Chromium, 7/7 реальный Nginx**, плюс 120 нагрузочных запросов / 12 пар / 3 одновременно / 0 неуспешных пар. Локальная нагрузка: 349 мс, p50 8 мс, p95 22 мс, максимум 56 мс. Audit npm: 0; diff --check без замечаний. Это не проверка пропускной способности канала или предельной ёмкости сервера; npm audit не проверяет контейнерные образы.

CI дополнен edge-тестами, nginx -t и smoke non-root/read-only контейнера, связкой с приложением и caddy validate. Здесь Docker отсутствует: контейнерный прогон и реальный TLS **не подтверждены**. Внешняя L3/L4-фильтрация/провайдер, firewall origin и оповещения не настроены. Прямой preview npm start не проходит через edge. Порядок подключения и честные границы: [DDOS.md](DDOS.md).
