# «Рядом» как мини-приложение MAX

Production также требует оператора, поддержку и опубликованные документы; настройка/preflight описаны в DEPLOYMENT.md. Версия согласия production — max-data-DATA_POLICY_VERSION, pilot-data-max-v1 используется только в разработке.

Основной канал продукта — **MAX**, не Telegram и не обычный сайт. В репозитории реализована интеграция Bridge и серверная авторизация. **Бот не зарегистрирован/не опубликован этой сессией, работа в настоящих клиентах MAX ещё не подтверждена.** Обычный браузерный preview — только среда разработки.

## Что подключено

- SDK `https://st.max.ru/js/max-web-app.js`, глобальный объект **window.WebApp**. Скрипт загружается при настроенном MAX_BOT_TOKEN; бот-токен в браузер не передаётся.
- POST `/api/max/auth`: сервер проверяет исходную строку `WebApp.initData`, двухэтапный HMAC-SHA256 с `WebAppData`, подпись постоянным по времени сравнением, возраст до часа и отклонение в будущее не более минуты. URL-декодирование однократное, дубликаты/неверные параметры отклоняются. `initDataUnsafe` для авторизации не используется.
- Каждый успешный запуск помечается в SQLite хешем проверенных user_id/query_id/auth_date. Перестановка параметров/другая URL-кодировка не позволяют обменять тот же запуск повторно. Уже действующая сессия того же профиля может подтвердить этот запуск повторно, но новый ключ не получает. После выхода/отзыва использованный запуск больше не выдаёт ключ: нужно закрыть и снова открыть мини-приложение.
- Первый вход требует согласия `pilot-data-max-v1`. Сохраняется только MAX user ID → профиль, не полные данные запуска, фото или телефон. Связь удаляется с профилем. Экспорт содержит собственный MAX ID, но не идентификатор близкого/ключи доступа.
- Существующий браузерный профиль связывается **только с отдельным подтверждением владельца**. Несовпадение уже связанных аккаунтов блокирует загрузку частного состояния, в том числе фоновый опрос. Автоматического слияния пар нет.
- Приглашение `https://max.ru/ИМЯ_БОТА?startapp=invite_КОД`; сервер использует подписанный `start_param`. Близкий входит своим MAX-аккаунтом и создаёт отдельный профиль. Два устройства одного аккаунта не заменяют два согласия. Уже существующий профиль не переезжает в другую пару из приглашения автоматически.
- Нативная отправка приглашения — `shareMaxContent`, кнопка «Назад» — `BackButton`, предупреждение о закрытии незаконченного занятия, учёт viewport/safe area. Попытка запретить захват экрана на экранах кодов/настроек через `ScreenCapture` — best effort, не гарантия защиты.
- Ключ хранится в `SecureStorage` при поддержке, иначе в localStorage WebView; при недоступном localStorage — до закрытия страницы в памяти. Хранилище не заменяет серверную проверку/отзыв.
- JSON-экспорт в нативном MAX через `downloadFile`: сервер выдаёт одноразовый HTTPS-адрес на **60 секунд**, без bearer-ключа в URL. HEAD не потребляет адрес; GET потребляет. Выход/отзыв сессии отменяет скачивание; повторный выпуск отменяет предыдущий. Временный файл находится в памяти одного процесса, после перезапуска недоступен.

## Что нужно владельцу для настоящего запуска

1. Доступ к кабинету MAX с правом создавать/настраивать бота. Требуемый статус и актуальные условия оформления уточняются в кабинете — здесь не предполагается, что у владельца они уже есть.
2. Реальный username бота (без `@`) и токен. **Токен задаётся только секретной переменной на сервере. Не присылайте его в чат, не коммитьте .env и не публикуйте вывод конфигурации с секретами.**
3. Постоянный сервер с доступным обоим участникам HTTPS-доменом, постоянным диском, копиями и мониторингом. Временный preview для эксплуатации не подходит.
4. Согласованные оператором документы/основания обработки, включая связь MAX ID с профилем: `LAUNCH.md`.

### Настройка окружения

| Переменная      | Назначение                                                                                                                  |
| --------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `MAX_BOT_TOKEN` | Секрет сервера для проверки подписи; без него MAX-вход возвращает 503                                                       |
| `MAX_BOT_NAME`  | Username именно того же бота, латинские буквы/цифры/подчёркивание, без @; используется в приглашениях                       |
| `MAX_ONLY=true` | Требовать подписанный Bridge-контекст в интерфейсе; запретить обычные register/join. Без MAX_BOT_TOKEN сервер не запустится |
| `PUBLIC_URL`    | Канонический HTTPS origin приложения для скачивания, например `https://рядом-ваш-домен.ru`                                  |
| `DATA_DIR`      | Постоянный каталог SQLite, отдельный от тестовых баз                                                                        |
| `TRUST_PROXY`   | Только адреса доверенного reverse proxy, см. DEPLOYMENT.md                                                                  |

Для Compose заполните приватный `.env` по `.env.example`, `chmod 600 .env`, затем `docker compose config --quiet` и `docker compose up -d --build`. Compose по умолчанию требует токен/имя и включает MAX_ONLY; PUBLIC_URL задаётся из APP_DOMAIN. **Docker/TLS здесь не запускались.**

Для обычного Node .env не загружается автоматически командой `npm start`. Используйте секреты процесса/хостинга или `node --env-file=.env server.js`; при этом задайте реальный PUBLIC_URL отдельно, как в примере. Разработческий `npm start` без MAX-переменных сохраняет обычный веб-режим для тестов.

В кабинете `business.max.ru/self`: **Чат-боты → ваш бот → настройки → HTTPS URL мини-приложения → подпись кнопки → сохранить**. Затем открыть приложение **из бота**, не просто отправить URL сайта сообщением. Включение мини-приложения и публикация/модерация — действия владельца, не выполняются одним добавлением файлов в Git.

Нельзя запускать тесты с производственными секретами/базой. Тесты MAX используют заведомо фиктивные отдельные токены и отдельные порты/SQLite.

## Ограничения и важные различия

- В нативном MAX не используются Blob + `<a download>` и `window.print` как будто это обычный браузер. Код восстановления предлагается скопировать в безопасное место, печать заменена понятным сообщением. JSON скачивается нативно. В web MAX нативный downloadFile не вызывается: одноразовый HTTPS-файл открывается внешним браузером через Bridge.openLink после действия пользователя. Это покрыто подменённым Bridge; реальная клиентская приёмка ещё нужна.
- В MAX основной способ повторного входа — **тот же аккаунт MAX**, поэтому анонимные формы восстановления/подключения устройства скрыты. Перенос существующего браузерного профиля работает, когда в WebView уже доступен его действующий ключ; отдельного переноса из другого браузера по коду с одновременной сменой MAX-аккаунта нет. Браузерные коды остаются механизмом веб-режима и аварийной эксплуатации, не способом обойти привязку MAX.
- До пяти подключений к одному профилю. Действующий сохранённый ключ переиспользуется; новый вход без него создаёт новое подключение. При лимите нужно отключить старое из оставшейся сессии.
- Отзыв ключа устройства не завершает сеанс самого мессенджера. Владеющий действующим аккаунтом MAX может снова войти с новым подписанным запуском. При краже устройства завершите его сеансы **также в MAX**.
- После удаления профиля использованный запуск не создаёт его повторно; новый запуск может создать новое пространство с новым согласием. Данные старого профиля не восстанавливаются автоматически.
- Приложение рассчитано на один процесс с SQLite. Общий лимит API — 180/мин/IP; MAX auth — 120/15 мин/IP. Лимиты и временные файлы в памяти, не распределённая защита от атак. Для большого общего NAT/промышленного сервиса нужна отдельная политика лимитов.
- SDK — внешний ресурс MAX; его сетевую доступность нужно проверить на телефонах. Не логируйте initData, Authorization и пути временных скачиваний на прокси/в аналитике.
- Нет webhook-обработчика, Bot API-рассылок, push-напоминаний, запроса контактов или скрытой регистрации через профиль близкого. Для открытия Mini App из кнопки бота webhook этому приложению не требуется.

## Завершение UI и обработка сбоев

Ошибки запуска не оставляют пользователя на неработающей главной: показывается отдельный адаптивный экран с повторным входом и ссылкой на настоящего бота из конфигурации. Поздняя загрузка SDK и временный отказ конфигурации восстанавливаются без перезагрузки страницы. При повторном подключении SDK обработчик нативного BackButton регистрируется заново.

Ожидание viewport ограничено 1 секундой, SecureStorage — 4 секундами, получения конфигурации — 8 секундами на этап. При отказе/зависании хранилища используется локальный fallback. Если localStorage переполнено или запрещено, запись/удаление ключа учитываются в памяти текущей страницы; старая локальная запись не возвращается как текущая в этой странице. Уже отправленную нативную операцию Bridge отменить нельзя.

API-запросы отменяются через 15 секунд, ошибки сети/не-JSON ответа прокси показываются пользователю. Ответы фонового чтения проверяются относительно текущего ключа и порядка запросов: старый ответ не восстанавливает профиль после выхода, старый 401 не стирает новый ключ.

## Что проверено автоматически

`test/max-ui.test.js`: зависшие viewport/storage, localStorage quota/удаление, HTTPS-only download/openLink и понятные ошибки Bridge. `test/interface.test.js` также проверяет повторный вход после временного отказа стартовой конфигурации.

`test/max.test.js`: настоящая HMAC-проверка и HTTP-вход, согласие, подпись/возраст/дубликаты, replay с перекодировкой, привязка профиля, два участника, запрет третьего, отсутствие автоматического перехода в другую пару, восстановление/удаление, HTTPS-экспорт и отзыв.

`e2e/max.spec.js`: настоящий Chromium и сервер MAX_ONLY с **подменённым Bridge**: вход/хранилище, отправка/назад/скачивание, два независимых MAX ID и дистанционная договорённость, несовпадение аккаунта без утечки через polling, ошибка без настоящего контекста. Desktop/mobile viewport — не настоящие клиенты MAX.

## Обязательная ручная приёмка в MAX (пока не выполнена)

- Android и iPhone, отдельно web MAX: открытие кнопкой бота, первый вход/согласие, закрытие и повторное открытие, reload.
- Приглашение из реального MAX-диалога: второй человек попадает в ту же пару и входит своим аккаунтом; отзыв ссылки работает.
- «Назад», клавиатура, safe area, крупный текст, прокрутка, сворачивание/возврат, медленная сеть и отсутствие CDN.
- Дистанционное занятие и отдельное согласие на одну версию текста у обоих.
- Скачивание на Android/iOS, отказ/таймаут Bridge, истёкший/повторный URL; отдельно открытие HTTPS-файла внешним браузером из web MAX.
- Выход, отзыв старой сессии, пять подключений, смена аккаунта MAX, перенос старого профиля с явным подтверждением, удаление и повторный запуск.
- Скринридеры и наблюдаемый тест с пожилыми участниками.

## После восстановления сервера

Старые ключи, коды и приглашения аннулируются; восстановленная копия недоступна до проверки оператором и release-restore. Затем нужно дождаться opensAt и заново открыть MAX: подписанные запуски до этой даты не принимаются. Полный порядок и ограничения: [RECOVERY.md](RECOVERY.md).
