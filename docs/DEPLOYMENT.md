# Развёртывание, резервные копии и восстановление

Это инструкция и конфигурация, а не подтверждение уже выполненного промышленного развёртывания. В среде разработки Docker отсутствует: сборку образа, Compose, Caddy, получение TLS-сертификата и внешний мониторинг здесь не проверяли.

Основной канал — MAX: сначала прочитайте [MAX.md](MAX.md). Compose требует секрет бота и его username, по умолчанию MAX_ONLY=true. `docker compose config` без --quiet может напечатать секрет: не публикуйте такой вывод.

## Проверяемый production-режим

В `NODE_ENV=production` сервер требует заполненные MAX_BOT_TOKEN/MAX_BOT_NAME, MAX_ONLY=true, абсолютный DATA_DIR, публичный HTTPS origin PUBLIC_URL (не localhost/.invalid/example.com), OPERATOR_NAME, SUPPORT_EMAIL, PRIVACY_POLICY_URL, TERMS_URL и DATA_POLICY_VERSION. Политика и условия должны быть реально опубликованы оператором. Проверка адреса не проверяет содержимое документа, его доступность, юридическую корректность или принадлежность домена.

`.env.example` включает NODE_ENV=production; Compose задаёт свои NODE_ENV/DATA_DIR. Для прямого Node создайте постоянный каталог с правами пользователя приложения. `npm start` .env не читает. Проверка без запуска сервера: `node --env-file=.env scripts/preflight.js`, затем `node --env-file=.env server.js`. Если окружение уже задано системой/хостингом, можно `npm run preflight` и `npm start`. Не публикуйте вывод `docker compose config` с секретами; используйте --quiet.

UI получает только публичные реквизиты оператора/почту/ссылки/версию, не bot token. MAX открывает ссылки через Bridge.openLink. Для новой редакции обработки измените DATA_POLICY_VERSION: версии согласия становятся max-data-ВЕРСИЯ/web-data-ВЕРСИЯ. Старые принятия не подменяются новыми автоматически, MAX-вход предложит повторное согласие. Это механизм учёта, не утверждение правовых оснований обработки.

Production добавляет HSTS max-age=31536000 (без includeSubDomains). Включайте его только на настоящем HTTPS-домене. Docker healthcheck использует `/readyz`: БД и права чтения/записи каталога, 503 при ошибке. Это не проверка свободного места, внешних копий, сети MAX или всей бизнес-функциональности — настройте их мониторинг отдельно.

## 1. До включения публичного доступа

- Назначить оператора сервиса и ответственного за инфраструктуру.
- Выбрать сервер и место хранения данных с учётом применимых требований. Российское размещение не возникает автоматически из Docker-конфигурации.
- Утвердить документы и правовые основания обработки; см. `LAUNCH.md`.
- Направить DNS реального домена на сервер. Открыть 80/443, закрыть прямой доступ к приложению и базе.
- Не публиковать БД, резервные копии, приглашения и коды восстановления.

## 2. Один сервер: Docker Compose + Caddy + edge

```sh
cp .env.example .env
# Заполнить домен, MAX-секрет, оператора, поддержку, адреса и версию документов.
chmod 600 .env
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app edge proxy
```

Caddy получает сертификат для APP_DOMAIN при корректном DNS и сетевом доступе. До проверки не считать HTTPS настроенным.

В Compose снаружи доступен только Caddy (80/443). Он отправляет трафик в Nginx edge через front `172.28.0.0/24`; edge — в приложение через отдельную backend `172.29.0.0/24` (internal). Порты edge/app не опубликованы. Nginx доверяет только front, приложение — только backend. При смене сетей обновить Compose, set_real_ip_from и TRUST_PROXY вместе. Caddy перезаписывает X-Forwarded-For адресом прямого соединения: для внешнего CDN нужна отдельная проверенная схема доверия и блокировка origin. [DDOS.md](DDOS.md).

Приложение работает без root, с read-only корневой ФС, постоянным томом данных и ограниченными по размеру контейнерными логами. `/healthz` проверяет ответ сервера и чтение SQLite. Docker healthcheck не отправляет уведомления сам: внешний мониторинг необходимо настроить отдельно.

SQLite рассчитана на один экземпляр приложения. Не масштабируйте реплики с отдельными дисками.

## 3. Автоматические шифрованные копии

В Compose добавлен `backup-worker`: немедленная первая копия, затем каждые 6 часов, 56 архивов, AES-256-GCM, проверка расшифровкой до ротации и отдельный healthcheck. **Перед `docker compose config/up` создайте ключ и задайте BACKUP_KEY_HOST_FILE:** полный порядок в [ENCRYPTED_BACKUPS.md](ENCRYPTED_BACKUPS.md). Подключите внешний контроль здоровья worker и передачу архивов на другой носитель/сервер; это не возникает автоматически из конфигурации.

### Ручная незашифрованная копия работающей базы

Ниже оставлен диагностический инструмент. Для штатного расписания используйте шифрованный worker, не этот cron.

На хосте с Node.js 22.16+:

```sh
DATA_DIR=./data npm run backup -- ./backups
```

В Compose после сборки образа:

```sh
docker compose --profile tools run --rm backup
```

Используется SQLite online backup API: копия учитывает зафиксированные изменения WAL без остановки приложения. Создаются файл `.sqlite` и `.sha256`; проверяется integrity_check. Файлы получают права 0600. Каталоги новых копий создаются с 0700. Уже существующие каталоги должны иметь безопасные права, ответственность за них — у оператора.

**Контрольная сумма проверяет повреждение, но не аутентичность.** Она не заменяет защиту от подмены. Копия содержит персональные данные и действующие хеши доступа: храните её в защищённом месте и передавайте вне сервера только по утверждённой процедуре, с шифрованием.

Пример локального расписания (пути заменить на реальные):

```cron
# Ежедневно в 03:00. Нужны проверка кода возврата и оповещение об ошибке.
0 3 * * * cd /srv/ryadom && /usr/bin/docker compose --profile tools run --rm backup
```

Это только пример. Cron, внешнее хранение, политика ротации, шифрование и оповещения **не развёрнуты автоматически**. Срок хранения копий должен соответствовать утверждённой политике, включая порядок удаления данных из архивов.

## 4. Проверка восстановления

Полный обязательный порядок: [RECOVERY.md](RECOVERY.md). Восстановление аннулирует все старые сессии, legacy-ключи, recovery, коды подключения и приглашения. Восстановленная БД публикуется только после проверки/сброса, атомарно и без перезаписи, с **закрытым API**. Даже настоящий старый ключ доступа не открывает восстановленный сервис.

Остановите приложение и используйте новый пустой постоянный каталог/том:

```sh
DATA_DIR=/srv/ryadom/data-restored npm run restore -- /secure-backups/ИМЯ.sqlite --confirm-stopped
```

Сверьте удаления/обращения и изменения после даты архива. Удалите данные, которые не должны вернуться. Без утверждённой процедуры и информации для этой сверки **не выпускайте** восстановленную копию.

После проверки, при остановленном приложении:

```sh
DATA_DIR=/srv/ryadom/data-restored npm run release-restore -- --confirm-stopped --confirm-reviewed
```

Release сообщает opensAt. Запустите приложение с полным production-окружением и новым DATA_DIR. До opensAt `/readyz`/API остаются 503; это защитное окно для исключения прежних MAX-подписей, в том числе с допустимым опережением часов. После opensAt нужен новый запуск Mini App из MAX, не старый код. `/healthz` — только liveness, не разрешение публикации. Проверьте пару, памятку и избранное.

Скрипты не умеют удостоверять, что все процессы действительно остановлены, и не выполняют сверку удалений за оператора. Веб-профили без MAX-привязки после сброса не восстанавливаются по старым кодам; случай нужно решить до выпуска без выдуманной проверки личности по имени. Реальные внешние архивы, их очистка, RPO/RTO и автоматическая сверка внешнего журнала не подтверждены.

## 5. Обновление и откат

1. Создать и проверить резервную копию до обновления.
2. Записать версию приложения/образа, время копии и ответственного.
3. Выполнить `docker compose up -d --build`, проверить healthcheck и ключевые сценарии.
4. Следить за ошибками и объёмом диска.
5. Для отката кода использовать предыдущий проверенный образ. Не считать обратную совместимость будущих миграций гарантированной.
6. Восстановление базы делать в отдельный пустой том с аннулированием старых доступов и обязательной сверкой удалённых данных до release-restore.

SIGTERM/SIGINT прекращает приём соединений и закрывает SQLite. Ожидание ограничено 10 секундами.

## 6. Мониторинг и поддержка — настроить перед запуском

- Внешняя проверка HTTPS `/healthz` и срока сертификата.
- Свободное место томов данных, копий и контейнерных логов.
- Успех/возраст последней копии; периодическая проба восстановления.
- Процесс реагирования: кто получает сигнал, сроки реакции, как остановить доступ.
- Запрет записи ключей, кодов, текстов занятий и приглашений в диагностические логи.
- Контакт поддержки, опубликованный в сервисе и документах оператора.

Встроенной панели мониторинга, внешних оповещений и службы поддержки в приложении пока нет.


## Постоянная защита от перебора

Счётчики API/восстановления/подключения перенесены в `DATA_DIR/security.sqlite`, не удаляйте файл при обновлении. Нужен локальный постоянный диск с правом записи. Счётчики не входят в основной backup приложения. Перед публикацией обновите документы и DATA_POLICY_VERSION с учётом сетевых HMAC-псевдонимов, в том числе до входа. Настройте доверие только своему reverse proxy. Границы и проверки: [RATE_LIMITS.md](RATE_LIMITS.md).


## HTTP-перегрузка и внешний DDoS

Включён edge-слой с per-source и aggregate квотами, лимитом одновременных запросов, 32 KiB тела и таймаутами. Политики, семь локальных проверок реального Nginx, ограничения NAT, доверие к IP и инструкция для внешнего фильтрующего провайдера — [DDOS.md](DDOS.md). Канал, SYN/UDP/TLS-flood и origin-firewall локальным лимитером не защищены автоматически. Внешний провайдер и оповещения пока не подключены.
